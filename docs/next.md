# Acrux 알파 (Tauri)

실험(알파) 버전입니다. 동기화 검토 기준 정식 버전은 PC V3.0.5 · 모바일 V1.4.24 (`origin/main`의 `2c2e9be`)이고, 알파는 정식 앱의 배포 · 자동 업데이트와 따로 움직입니다. 정식 소스 전체를 개발 브랜치에 덮어쓰지 않고 아래 기록에 따라 필요한 동작을 이식합니다.

- 코드: `src-tauri/` (Rust 엔진 · 기기별 입력 · 캡처 · Android 셸) · `frontend/` (TypeScript 화면)
- 번역: `frontend/main.ts` 가 `android/app/src/main/assets/i18n/` 의 tsv 를 읽음 → 번역은 `android/tools/mobile_i18n.py` 에 행을 추가하고 tsv 를 다시 만들어서 같이 커밋
- 정식 앱 로직 (낚시 · 이동 · 바이옴 · 판매) 을 바꾼 커밋은 제목에 `[port]` → 알파에도 옮긴 뒤 아래 '옮긴 커밋' 에 적기

## 개발 브랜치와 기기 테스트

- `dev`는 크로스플랫폼 개발용 브랜치입니다. 기존 `Crossplatform-test`를 이름 변경했습니다.
- `main`은 정식 PC Python 앱과 모바일 Java 앱의 패치·배포 기준입니다. 정식 앱의 수정은 `dev`에 이식하고 아래에 이식 기록을 남깁니다.
- DUA(Device Use Agent)를 매크로의 주 실행 경로로 개발합니다. Linux 데스크톱 실행 경로는 앱이 관리하는 독립 Gamescope/XWayland 세션이며, Android도 공통 Rust DUA로 자동 보정·낚시·상태별 관측을 연결했습니다. Android 입력은 잠금 해제된 Roblox 전경 화면에서만 허용하며 다른 앱에서는 대기합니다. Windows·macOS의 독립 입력 연결은 아직 지원하지 않습니다.
- 테스트는 크로스플랫폼 빌드·회귀 검사와 실제 기기에서의 시작·설정·보정·매크로 실행 확인을 함께 사용합니다. 기기·OS·앱 버전·결과를 기록하고, 기기에 접근할 수 없는 항목은 미검증으로 기록합니다.
- Linux·Windows·Android·macOS가 빌드·검사 대상입니다. iOS는 빌드·실행 검사에서 제외합니다.
- `dev`의 Android·Windows·Linux·macOS 빌드 결과는 GitHub Actions 실행의 첨부 파일로 받습니다.

## 현재 상태

Android의 TypeScript 화면은 기존 모바일 탭과 카드를 재현하고, 데스크톱은 PC 3.0.0의 HTML·CSS를 TypeScript를 통해 Tauri에 연결합니다. 모바일의 기존 터치·숫자 저장 수정은 유지하며 홈과 조작 창의 시작·정지를 공통 DUA로 연결했습니다. Linux는 전용 세션의 정지 낚시, Android는 전경 입력을 제한한 자동 보정·낚시 실행 경로를 구현했습니다. Android 실제 게임 낚시 검증은 진행 중입니다. Windows·macOS의 독립 입력 연결과 Python 모드 실행·복구·게임 입장 자동화는 준비 전입니다.

- `npm ci` 후 `npm run build`로 화면을 빌드합니다.
- Windows에서는 `npm run tauri -- dev`로 실행하거나 `npm run tauri -- build`로 패키징합니다.
- Linux에서는 `npm ci` 후 `npm run build:linux -- --ci`로 빌드합니다. 실행 파일은 `src-tauri/target/release/acrux`이며 Sober 연결 조건은 아래를 참고하세요.
- Android에서는 JDK 17, Android SDK 36, NDK와 Rust의 `aarch64-linux-android` 타깃을 준비한 뒤 `npm run tauri -- android build --apk --target aarch64 --debug`를 실행합니다. 테스트 패키지 `com.acrux.next`는 기존 앱과 별도로 설치됩니다.

Android 미리보기에는 DUA 자동 보정·낚시, 바이옴 감시·디스코드 알림 흐름이 들어 있습니다. 홈에서 실제 실행 경로·판단 이유·Headless 처리·스크린샷 처리·경로 전환 횟수와 Roblox 입력 가능 상태를 표시합니다. Android와 데스크톱 모두 이전 시간 기반 이동·자동 판매를 비활성화했으며, 저장 좌표·경로·시간 값은 보존하고 자동 실행 플래그를 끕니다. 모바일의 관련 토글·숫자 입력·실행 가이드는 비활성화하고 준비 중으로 안내합니다. 조작 창의 이전 이동·판매 테스트도 실행하지 않습니다.

Android의 바이옴 기능은 앱 내부 무선 디버깅 페어링과 로그 수집을 사용합니다. 로그 재연결 시 이어 읽기와 2분 정체 감지, 웹후크별 순차 전송·429 재시도를 포함합니다. 사용자 수는 `https://acruxmacro.com/api/`에서 읽습니다.

판매 자동 보정, 조이스틱 자동 검색, PC의 Python 모드 실행·복구·게임 입장 자동화와 나머지 PC 전용 자동화, 기존 정식 앱 설정 이전, 배포 업데이트는 아직 이식 전입니다. 모드 화면은 실행 미지원 상태를 표시합니다. Android와 데스크톱의 새 지도 이동·판매 실행은 아직 연결 전이며, 이를 기존 시간 경로 재생으로 대신하지 않습니다.

### Android DUA 시작 흐름

1. 홈의 준비 카드에서 접근성 권한과 화면 캡처를 켭니다. 캡처 공유는 전체 화면을 선택합니다.
2. Roblox의 Sol's RNG를 가로 전체 화면으로 열고, 낚시 가능한 해안에서 Fish 버튼이 보이도록 직접 자리를 맞춥니다. 자동 해안 탐색이나 지도 이동은 아직 연결하지 않았습니다.
3. 앱 홈 또는 Roblox 위 Acrux 조작 창에서 시작을 누릅니다. 두 버튼은 같은 Rust DUA를 실행하며, 저장된 보정이 없으면 자동 보정한 뒤 낚시를 이어갑니다. 수동 보정도 조작 창의 낚시 메뉴에 남아 있습니다.
4. 앱 홈에서 시작한 직후처럼 Roblox가 앞에 없으면 DUA는 Headless로 기다립니다. Roblox가 앞에 오면 새 화면을 관측한 뒤 진행합니다. 다른 앱으로 전환하면 실행 세대를 바꿔 이전 입력·대기 중 관측을 폐기하고 기다리며, 화면이 꺼지거나 잠기면 중지합니다. 잠금 해제만으로 다시 시작하지 않습니다.
5. 홈 또는 조작 창의 정지로 멈춥니다. 시작 응답이나 숫자 설정 저장을 기다리는 동안에도 정지 요청을 보낼 수 있으며, 늦게 도착한 응답이 실행 상태를 되살리지 않게 합니다. 인벤토리가 가득 차면 중지하며 자동 판매·이동은 실행하지 않습니다.

이 Android 실행 경로는 기기 밖의 독립 게임 세션이나 다른 앱과 동시에 터치하는 백그라운드 입력이 아닙니다. `gameAvailable`은 잠금 해제된 Roblox 전경 여부를 반영하고, `dua.background`는 `false`입니다. 낚시 판단은 공통 Rust의 상태·색상·형상 규칙을 사용하며 AI 모델이나 추론 API를 추가하지 않았습니다.

관측 시각과 ROI는 공통 DUA가 요청합니다. Android는 최신 프레임 하나를 보관하고 기한·실행 세대를 검사하며, Screenshot 요청이 있을 때 필요한 픽셀을 Rust에 전달합니다. 전체 관측은 열린 Image의 직접 버퍼를 사용하고, ROI 관측은 요청 영역만 재사용 버퍼로 복사합니다. Headless 대기에서는 낚시 화면 분석을 요청하지 않습니다. 다만 OS의 전체 화면 MediaProjection·VirtualDisplay·ImageReader 버퍼와 게임 렌더링은 계속 존재합니다. 실제 부분 화면을 OS에서만 캡처하는 구현이나 앱 전체 메모리 절감률을 검증한 결과로 해석하지 않습니다.

### 모바일 DUA 검증 · 2026-11-13

현재 변경에서 Rust 일반 검사 94개와 별도로 실행한 네이티브 검사 2개, 프런트 검사 37개, Python 회귀 검사 5개 및 Windows 타깃 코드 검사를 통과했습니다. 프런트 검사는 모바일의 미보정 시작·Roblox 전경 대기·DUA 유휴 단계 중 정지·시작과 정지의 경합·숫자 저장 중 정지·실제 경로/횟수 표시·비활성 이동 설정 보존을 포함합니다.

Android ARM64 release APK를 빌드해 SM-S931N의 Android 16에 설치했습니다. 기기에서 DUA 시작 후 Headless 대기를 관측했으며, 실제 스크린샷에서 오른쪽 리더보드를 더 큰 낚시 패널로 잘못 선택하는 문제를 재현해 중앙 위치 검증과 저장된 오답 좌표의 입력 차단·전체 화면 재탐색을 추가했습니다. 조작 창의 유사 테두리·버튼도 인식에 끼어들지 않도록 캡처에서 제외했습니다. 화면 전환으로 생긴 이전 캡처는 실행 세대별 새 ImageReader 스트림으로 차단합니다. 실제 PNG 두 장에서 수정 후 올바른 Fish 좌표를 검출했습니다. 이어 기기에서 던지기·입질·릴링·획득 결과창 닫기·재던지기 반복을 확인했으며 첫 연속 실행의 앱 집계는 성공 4·쓰레기 1·실패 0이었습니다. 이는 짧은 기능 검사이며 장시간 성공률 측정이 아닙니다. 다른 앱으로 전환한 3초 동안 Headless 처리만 1843→1855로 늘고 스크린샷 처리는 1770으로 유지됐습니다. 게임 복귀 후 다시 관측했고 정지 버튼도 확인했습니다. 전환 테스트 중 Roblox 자체 로그에서 백그라운드 약 30초 후 게임 종료를 확인했으므로 화면을 숨긴 채 게임을 유지하는 지원으로 해석하지 않습니다.

입질 대기의 배경색을 릴링 바로 오인하는 실제 PNG도 재현해 Fish/Exit가 보이면 릴링 후보를 무시하도록 수정했습니다. 동일 대기 PNG 네 장을 1.5초씩 재생했을 때 이전 14회 터치가 0회로 줄었고, 실제 릴링 PNG는 그대로 인식했습니다. 재개 시 제목과 실제 X가 검증된 결과창은 기존 닫기·통계 처리로 보냅니다. 실제 복귀 PNG에서 첫 관측에 X 좌표를 찾았고 신규 회귀 두 개를 통과했습니다. 최종 APK를 다시 설치해 보정 초기화→자동 보정→던지기→정상 입질 대기를 실기기에서 확인했습니다. 이 APK에서 새 자동 보정 후 성공 2·쓰레기 0·실패 0의 반복 실행을 확인했습니다. 앱 전환 3초 동안 스크린샷 처리는 1153으로 유지되고 Headless만 1286→1298로 증가했습니다. 복귀 첫 관측을 항상 전체 화면으로 바꾸는 추가 회귀를 통과했으며, 그 수정 APK의 별도 실기기 재개 검사에서는 결과 발생 뒤 복귀 시 0.8초 안에 다음 던지기로 이어졌습니다. 검사가 끝난 매크로는 정지했습니다.

전체 Android 화면 버퍼 비용과 장시간 CPU·메모리·성공률 측정, 화면 잠금 후 실제 재시작 검사는 이번 검사 범위에 포함하지 않았습니다. APK·스크린샷·로그는 로컬 `out/mobile-dua-20261113/`에 보관하고 저장소에는 올리지 않습니다.

### 백그라운드 DUA 1차 교체

기존 낚시 상태·릴링 제어·설정 저장 형식을 재사용하고 데스크톱 실행 연결을 교체했습니다. Linux는 앱의 전용 Gamescope headless/XWayland 세션만 연결합니다. 사용자 DISPLAY로 되돌아가는 입력 폴백과 Windows의 공유 SendInput 실행기를 제거했습니다. 독립 연결이 없는 데스크톱 플랫폼은 준비되지 않았다고 표시합니다. 이후 Android DUA 적용은 위 절에 기록하며, main의 정식 Python·Java 앱은 변경하지 않습니다.

- 앱의 게임 열기/닫기와 세션 상태를 연결했습니다. 실행 중인 기존 Sober는 자동으로 종료하지 않고 시작을 거절합니다. 전용 X11 인증·프로세스 소유권·시작 취소·종료 핸들을 확인하며, 앱 종료와 오류에서도 소유한 세션만 정리합니다. 시스템의 다른 Flatpak 앱이나 전체 Sober 앱 ID를 일괄 종료하지 않습니다.
- 전용 게임 미리보기는 원시 픽셀을 약 2fps로 한 요청씩 표시합니다. 매크로 중지 상태에서는 키·클릭·시점 조작을 전용 화면에 전달하고, 매크로 실행 중에는 보기만 허용합니다. 입력 큐는 상한을 두고 시점 이동은 최신 값만 유지합니다. 닫기·포커스 이탈·실행 세대 변경 시 수동 입력을 해제하며 기한이 지난 요청은 전송하지 않습니다. 기존 Python 화면에는 이 기능을 노출하지 않습니다.
- 관측은 상태별 시각과 원본 좌표의 ROI를 전달합니다. X11은 실제 부분 GetImage를 요청하고 Frame::region이 전체 화면 크기·원점을 유지합니다. 화면에 없는 픽셀을 인식 근거로 만들지 않으며, 보정·재탐색 때만 전체 화면을 읽습니다. 결과창은 제목과 실제 X를 확인해야 클릭합니다.
- pathfinding 코어는 공급/관측된 볼록 지형·층·경사·높이·장애물과 검증된 점프 연결을 받아 목표 원/허용 영역까지 모서리 가시성 그래프 경로를 구합니다. 충돌 반경과 여유를 적용하며 직선 거리와 경로 길이를 별도로 반환합니다. 거리 기준은 명시된 수평 지도 모델이고 전역 3D 최단 경로라고 주장하지 않습니다.
- travel 코어는 실제 새 위치·방향·접지 관측으로 제한된 회전·직진과 계획된 점프 의도를 판단합니다. 오래된 관측, 위치 오차, 경로 이탈, 정체와 착지 실패 시 재관측·중지를 요구합니다. 픽셀을 지도 위치로 바꾸거나 카메라 회전량을 임의로 만들어 내지 않습니다.

### 이전 전경 DUA 기록

다음은 교체 전 구현과 검사 기록입니다. 현재 백그라운드 지원 범위로 해석하지 않습니다.

기존 메인 화면의 매크로 시작 버튼이 TypeScript 연결부의 `desktop_start`를 통해 Rust DUA를 시작합니다. DUA는 기존 낚시·이동·판매 엔진을 사용하면서 작업 상태에 따라 다음 실행 경로를 고릅니다. 판단은 코드에 정의한 규칙으로 수행하며 AI 모델·추론 API를 추가하지 않았습니다. 이번 구현은 `dev`에 적용하며 정식 `main`의 Python·Java 앱은 변경하지 않습니다.

- **Headless**는 내부 작업 상태와 구조화된 이동·키 입력·대기를 처리합니다. 이 경로에서는 게임 화면 캡처를 획득하거나 읽지 않습니다. 데스크톱 입력은 대상 게임 창이 앞에 있을 때 수행합니다.
- **Screenshot**은 자동 보정, 낚시의 던지기·입질·릴링·결과, 판매 화면의 확인 단계에서 캡처를 요청합니다. 구조화된 이동·대기 단계로 넘어가면 Headless로 돌아갑니다. 판매도 이동·대기 전체를 계속 캡처하지 않고 화면 확인 단계에서만 캡처를 사용합니다.

보정값이 없으면 낚시를 시작하기 전에 자동 보정하고 이어서 낚시합니다. 낚시 장소 이동을 설정했으면 해당 이동을 마친 뒤 보정합니다. 현재 실행할 수 있는 기능은 자동 낚시와 이에 연결된 이동·판매입니다. 다른 기능이 함께 켜져 있거나 실행할 기능이 없으면 시작 요청을 오류로 반환합니다. 설정 화면의 기존 세부 기능들은 이식 상태에 따라 별도로 구현해야 합니다.

공통 위치 화면의 DUA 패널에는 현재 경로·판단 이유·Headless 처리 횟수·실제 스크린샷 처리 횟수·경로 전환 횟수와 정지 방법을 표시합니다. 메인 매크로 타일도 DUA 상태를 우선 표시합니다. 실행 중 활성 기능 목록을 바꾸면 중지하고 다시 시작하도록 안내하며, 일반 설정 편집으로 실행 중인 DUA를 다시 시작하지 않습니다.

메인 정지 버튼으로 실행을 중지합니다. Windows와 X11/XWayland에서는 F3·F7도 사용할 수 있습니다. 네이티브 Wayland에서는 다른 앱의 키보드 상태를 읽지 않으므로 앱의 정지 버튼을 사용하며, 화면에서도 사용할 수 없는 단축키 대신 앱 버튼을 안내합니다. 중지하거나 작업을 전환하면 실행 세대를 바꾸어 이전 작업에서 계산한 입력이 뒤늦게 실행되지 않게 합니다. 캡처·입력 직전에는 대상 창과 크기를 다시 확인하며 이동 중 창 크기가 바뀌면 해당 경로를 중지합니다.

당시 게임 캡처·입력 연결은 Windows와 Linux의 X11/XWayland·Hyprland Wayland Sober에 있었으며 Android DUA는 후속 작업이었습니다. 현재 데스크톱 지원 범위는 위 '백그라운드 DUA 1차 교체', Android 적용은 'Android DUA 시작 흐름'을 따릅니다. iOS는 빌드·실행 검사에서 제외합니다.

Windows DUA 도입 때 `npm run build`, `npm run test:desktop` 11개, Rust 코어 검사 27개 (Windows는 시작 요청 세대 검사까지 28개), Python 회귀 검사 5개와 Windows 타깃 코드 검사를 통과했습니다. 검사는 두 루트의 전환, 캡처 없는 이동·대기, 판매 확인의 캡처 요구와 판매 후 낚시 복귀, 보정 후 낚시 재개, 중지·창 크기 변경·이전 입력 취소와 화면 연결부의 시작·오류 처리를 포함합니다. Linux 앱을 별도 임시 설정으로 빌드하고 5초 시작·설정 초기화를 확인했습니다. 브라우저에서는 시험용 상태 응답으로 두 경로 패널의 표시를 확인했습니다. 실제 Roblox에서 낚시·이동·판매 동작은 미검증입니다. 아래 Apple 실행 기록은 DUA 도입 전 커밋의 결과입니다.

### 백그라운드 DUA 개편 기준

사용자가 다른 프로그램을 쓰는 동안 전경 창, 실제 커서와 키보드 상태에 영향을 주지 않는 것을 우선 조건으로 합니다. 백그라운드 캡처와 입력 분리는 별개이며, 기존 전경 입력의 전면 창 검사를 없애는 것으로 구현하지 않습니다. 새 실기 입력 검사는 독립성을 확인한 실행 환경에서 진행합니다.

- 게임 클라이언트는 하나만 실행합니다. Linux에서는 앱이 관리하는 독립 디스플레이 세션 안에서 Sober와 입력 작업자를 함께 실행하는 방식을 먼저 검증합니다. Gamescope의 개인 XWayland 환경·headless 백엔드를 연결했고, 이 컴퓨터에서는 공식 Arch 패키지 서명을 확인한 실행 구성 요소를 개발 앱 옆에 준비했습니다. 기존 Sober를 종료하거나 다시 실행하지 않았습니다. Windows와 macOS도 플랫폼별 입력 분리를 별도로 확인해야 합니다.
- DUA의 Headless 경로는 확인 가능한 로그·상태·시간 조건을 처리합니다. 시각 확인이 필요한 이동은 지도와 지형 표식을 이용한 위치 추정 → 짧은 이동 → 재관측·보정 → 도착 확인으로 바꿉니다. 카메라의 높이·회전·확대를 표준화하고, 현재 위치와 경로가 가려지거나 모호하면 재탐색·중지합니다. 탑뷰 한 장으로 모든 지형과 임의의 위치를 항상 알 수 있다고 가정하지 않습니다. 점프가 필요한 구간은 접근 전에 경로에 포함하고, 도약 위치·높이차·통과 공간·착지 지점을 확인합니다. 벽에 부딪힌 뒤 점프하는 것을 이동 방식으로 사용하지 않습니다. 충돌하거나 진행이 없으면 입력을 멈추고 위치와 경로를 다시 확인합니다.
- 낚시 목표는 고정된 장소 좌표가 아니라 현재 위치에서 접근 가능한 해안가 영역입니다. 이미 바닷가 근처에 있고 낚시 UI가 뜨면 이동을 생략하고, 이동이 필요하면 도달 가능한 해안 후보를 선택한 뒤 실제 낚시 UI로 가능 여부를 확인합니다. 판매·제작·메모리 매치의 시설 위치와 낚시 가능 영역을 구분합니다. 기존 상태 엔진과 릴링 제어는 재사용합니다. 패널 내 고정 비율로 추정하던 부분을 실제 관측한 버튼·막대·표식 영역과 좌표로 바꾸고, 확실하지 않을 때만 넓은 영역을 다시 찾습니다. 앞서 정한 AI 미사용 조건을 유지하며 색상·형상·연결 요소·시간 변화에 따른 영역 분할로 시작합니다. 성공률은 실제 게임에서 별도로 측정합니다.
- 전체 화면을 매번 읽는 경로부터 줄입니다. 관측 요청에 필요한 시각과 영역을 연결하고, 지원하는 백엔드에서는 실제 부분 캡처를 합니다. 이미 전체 화면을 읽은 뒤 자르기만 하면 전송·전체 복사 비용은 남습니다. 새 전용 X11 연결은 필요한 영역만 GetImage로 읽습니다.
- 상태별 관측 주기와 게임 렌더링 주기를 따로 관리합니다. 입질 감시에 필요한 최소 관측을 유지하고 릴링 중에만 정밀 추적합니다. 오래된 프레임을 쌓거나 일상적인 프레임을 PNG·base64로 인코딩하지 않습니다. 지도 인식은 이동이 필요할 때 수행하고, 사용자 미리보기는 요청할 때만 제공합니다. DUA가 Headless인 동안에도 게임 자체의 렌더링 비용은 남습니다.

교체 전 네이티브 Wayland 캡처에서 physical=logical 1080p일 때 SHM·원본 Vec·정규화 Vec의 픽셀 버퍼가 겹치는 순간은 약 23.73MiB로 계산됐습니다. 현재 백엔드나 전체 앱·GPU 메모리를 측정한 값은 아닙니다. 게임 단독, 게임+독립 디스플레이, 게임+독립 디스플레이+DUA를 같은 해상도·장면에서 비교해 CPU·PSS/RSS·GPU/VRAM·실제 캡처 빈도·관측/입력 지연과 성공률을 기록합니다. 게임을 두 개 실행하거나 전체 자원이 두 배라고 가정하지 않으며, 측정 전 절감률도 주장하지 않습니다.

독립 실행의 통과 조건은 사용자가 다른 창에서 마우스·키보드를 쓰는 동안 게임 캡처와 클릭·키 해제가 작동하고, 호스트의 포커스·커서·누른 키에 변화가 없으며, 중지·연결 오류 뒤에도 입력이 남지 않는 것입니다. 이 조건을 먼저 확인한 뒤 지도 이동과 영역 인식을 연결합니다. 관련 근거: [Gamescope의 독립 XWayland 환경](https://github.com/ValveSoftware/gamescope#gamescope-the-micro-compositor-formerly-known-as-steamcompmgr), [headless 구현](https://github.com/ValveSoftware/gamescope/blob/master/src/Backends/HeadlessBackend.cpp), [Windows 공유 입력 스트림](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput).

### 목표 중심 거리원과 고무줄 경로

이동 설계는 목표 중심에 거리 기준 원을 표시하고, 관측한 아바타 발 위치에서 중심까지 선을 그어 직선 거리를 확인하는 방식을 따릅니다. 화면 픽셀 길이는 카메라 보정을 거쳐 지도 좌표로 환산합니다. 실제 이동 경로는 지형의 통과 가능 공간 위에서 팽팽한 줄처럼 장애물 모서리를 따라 꺾이는 최단 경로로 구합니다. 거리 표시 원과 별도로 기능별 도착 허용 범위와 상호작용 조건을 둡니다. 낚시에는 접근 가능한 해안가 영역을 목표 후보로 사용합니다.

1. 지형을 통과 가능한 면과 경계로 만들고 언덕의 높이·경사·단차·층을 함께 표현합니다. 벽·절벽·모서리에는 아바타 충돌 반경과 위치 추정 오차만큼 여유를 확보합니다. 화면에서 겹쳐 보여도 높이가 다른 지면은 별개로 취급합니다.
2. 아바타와 목표 사이의 직선이 이 이동 가능 공간을 통과하면 바로 잇습니다. 막히면 유효한 모서리와 면의 연결을 검색하여 우회 방향을 비교합니다. 작은 평면 지도는 모서리 가시성 그래프, 넓거나 다층인 지형은 내비게이션 메시와 연결 구간을 사용합니다. A*는 통과 경로를 찾는 검색 수단으로 사용합니다.
3. 통로가 선택되면 Funnel/string-pulling 방식으로 불필요한 중간점을 줄이고, 통과 가능한 모서리에만 줄이 걸리도록 경로를 당깁니다. 단일 통로를 당긴 결과만으로 전체 지도의 전역 최단 경로라고 부르지 않습니다. 거리는 확인된 지형 모델 기준이며, 시간·위험 가중 비용을 최소화하는 정책은 거리 최소화와 구분합니다.
4. 점프는 미리 확인한 도약·착지 구간을 잇는 방향성 연결로 경로에 포함합니다. 줄을 당길 때 그 연결을 지우거나 언덕·낭떠러지·다른 층을 직선으로 가로지르지 않습니다. 도약 전에 정렬하고 점프 후 착지를 확인합니다. 충돌은 재관측·재탐색 조건입니다.
5. 이동 중 실제 발 위치·경로 이탈·남은 경로 길이를 확인합니다. 목표 중심까지의 직선 거리는 참고값이며, 도착은 올바른 지면의 허용 영역 진입과 해당 기능의 실제 UI로 확인합니다. 목표가 영역이면 그 영역의 도달 가능한 부분까지 직접 탐색합니다.

이 기준의 경로 계산·피드백 판단 코어는 구현했습니다. 실제 게임의 지도·위치 관측 및 카메라/입력 연결은 아직 구현 중입니다. 참고: [Detour 통로 탐색·직선 경로 명세](https://recastnav.com/classdtNavMeshQuery.html), [string-pulling 구현](https://github.com/recastnavigation/recastnavigation/blob/main/Detour/Source/DetourNavMeshQuery.cpp).

### Linux · Sober 실행

개발 앱의 DUA 패널에서 백그라운드 게임을 열고 전용 게임 화면으로 접속과 초기 위치를 준비합니다. 기존 Sober가 실행 중이면 전용 게임을 추가로 띄우지 않습니다. 앱은 실행 구성 요소로 시스템 Gamescope 또는 실행 파일 옆 runtime/usr/bin/gamescope를 찾습니다. 이 환경의 보조 구성 요소는 공식 배포 서명을 확인한 Arch gamescope 3.17.0과 libxres 패키지이며 시스템 설치나 호스트 입력 설정을 바꾸지 않았습니다. 다른 Linux 배포판용 실행 구성 요소 패키징은 별도입니다.

일반 코어 검사는 실제 기기에 입력하지 않습니다. 독립 X11 검사는 명시적인 ACRUX_X11_TEST=1과 전용 DISPLAY=:90 이상을 요구합니다. 새 독립 Gamescope 검사는 실제 개발 실행 파일의 내부 --acrux-private-probe 모드와 ACRUX_SESSION_TEST=1을 요구하고, Sober 대신 별도의 그림 창을 사용합니다. 이 검사는 전용 인증·픽셀 캡처·부분 캡처·키/클릭·소유한 프로세스 종료를 확인하며 Sober 게임 호환성의 증거로 대신하지 않습니다.
